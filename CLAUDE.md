# GitHub Auditer

## Project overview
Python CLI tool for auditing and managing GitHub repositories across personal and organisation accounts. Uses the GitHub REST API via httpx. Multi-account support with YAML configuration. Designed to grow into a suite of mass-operation tools (add licenses, bulk archive, profile README wizard).

## Architecture
- **src/auditer/** — Python package (installed as `auditer` CLI via Click)
- **src/auditer/commands/** — CLI command implementations, organized into subdirectories by domain:
  - **commands/data/** — data acquisition & analysis (checkout, audit, activity)
  - **commands/repo/** — repository management (archive, settings, topics, add_license)
  - **commands/people/** — people & permissions (members, collaborators, access)
  - **commands/meta/** — configuration & utility (config_cmd)
  - **commands/content/** — content generation (profile, readme)
- **src/auditer/git_provider.py** — `GitProvider` Protocol (structural interface for git hosting API clients) + `get_provider(account)` factory that returns a `GitHubClient` or `BitbucketClient` based on `account.provider`
- **src/auditer/bitbucket_client.py** — `BitbucketClient`, Bitbucket Cloud REST API v2.0 client satisfying the `GitProvider` Protocol in full (verified via `isinstance(client, GitProvider)`), including the write/permissions methods `update_repo()`, `create_or_update_file()`, `get_file()`, `list_collaborators()`, `list_org_members()` needed for parity with `settings`/`readme`/`add-license`/`access`/`collaborators list`/`members list`. Wired (via `get_provider()`) into `checkout`/`audit`/`activity`/`settings`/`readme`/`add-license`/`access`/`collaborators list`/`members list` — only `collaborators add`/`collaborators remove` and `members remove` still hardcode `GitHubClient` directly, each guarded to print an explicit error and exit on Bitbucket accounts instead (see command-details sections below for coverage and gaps)
- **src/auditer/reports/** — Report generators (Markdown, future: JSON)
- **src/auditer/utils/** — Security (token masking), logging (sanitised output)
- **tests/** — pytest test suite with respx for HTTP mocking, command tests mirror source structure in `tests/commands/`
- **data/** — local checkouts split into `data/{slug}/public/` and `data/{slug}/private/` (gitignored)
- **reports/** — generated Markdown reports in `reports/{slug}/` (gitignored)

## Conventions
- Python 3.10+, httpx for HTTP, Click for CLI, Rich for terminal output, PyYAML for config
- Authentication via `config.yaml` (gitignored) — see `config.example.yaml` for template
- All scripts use `GIT_ASKPASS` for git auth — tokens NEVER embedded in URLs
- All subprocess calls use list form — NEVER `shell=True`
- All log output passes through `sanitise_git_output()` to strip leaked tokens
- Rich Console uses `soft_wrap=True` and `force_terminal=True` — do NOT add Rich line wrapping; let the terminal handle wrapping naturally. Output must also include ANSI codes for color when redirected to log files (for `tail -f` viewing).
- httpx/httpcore loggers are suppressed to WARNING level — do NOT log HTTP request details at INFO
- CLI entry point: `auditer` (defined in pyproject.toml `[project.scripts]`)
- Run with: `auditer <command> [options]`
- Tests: `pytest` (with respx for HTTP mocking)

## Security rules
1. `config.yaml` is gitignored — NEVER committed
2. Tokens NEVER embedded in URLs — use `GIT_ASKPASS` for git auth
3. All subprocess calls use list form (never `shell=True`)
4. All log output passes through `sanitise_git_output()` to strip leaked tokens
5. Token masking: `mask_token()` shows only last 4 chars
6. Token validation on startup: `GET /user` to verify PAT works before proceeding
7. Regex patterns catch all GitHub token formats (ghp_, github_pat_, gho_, ghs_, ghu_, ghr_)

## LazyConfig pattern
`cli.py` uses a `LazyConfig` class that defers `load_config()` until a command actually accesses `ctx.obj["lazy_config"].config`. This allows `--help` to work without a valid config file present. The `config` command is special — it accesses `ctx.obj["config_path"]` directly and calls `load_config()` itself.

## Third-party account support
Accounts where the token holder differs from `account.username` are third-party accounts (tracking someone else's public repos). `GitHubClient` caches `_authenticated_login` from `validate_token()` and uses `_is_own_account()` (case-insensitive comparison) to pick the `list_repos()` endpoint:
- **Org accounts**: always `/orgs/{username}/repos`
- **Own account** (token holder == username): `/user/repos` (returns private + public repos)
- **Third-party account** (token holder != username) or no token: `/users/{username}/repos` (public repos only, token still provides higher rate limits)
If `validate_token()` wasn't called before `list_repos()`, `_is_own_account()` triggers it lazily.

## Config command details
Flat command with `--validate` and `--show` flags. `--validate` loads and validates config.yaml, reports account count. `--show` displays defaults and a Rich table of all accounts with masked tokens, included repos, excluded repos, data_dir overrides. Uses `load_config()` directly (not `LazyConfig`).

`load_config_from_dict()` validates `provider` (`"github"` or `"bitbucket"`, default `"github"`) per account. Bitbucket accounts additionally require `workspace` and `auth_email` (`ConfigError` if either is missing). `type` is still a required field for every account regardless of provider (`slug`/`type`/`username` are checked first, before provider-specific validation) — for bitbucket accounts its *value* isn't checked against `"user"`/`"org"` (that check is GitHub-specific), but the key must still be present with some string value.

## Checkout command details
The `checkout` command provides detailed change reporting:
- **`--full`** flag: shorthand for `--branches --tags`
- Per-repo display: branch updates with commit count/authors, force push detection, new branches/tags
- GitHub URLs: compare URLs for branch updates, commit URLs, tree URLs for branches, release URLs for tags
- Tunable display constants at top of `checkout.py`: `MAX_COMMITS_SHOWN`, `MAX_SUBJECT_LENGTH`, `MAX_REFS_SHOWN`, `SUMMARY_WIDTH`
- `GitOpResult` dataclass holds success/message plus `new_branches`, `branch_updates` (list of `BranchUpdate`), `new_tags`
- `BranchUpdate` dataclass holds per-branch detail: `name`, `old_hash`/`new_hash`, `commit_count`, `authors`, `commits` (list of `(hash, subject, author)` tuples), `forced`, `removed_count`
- `_parse_fetch_output()` extracts refs from git fetch stderr; `_get_commit_details()` runs `git log` with `\x1e` field separator (uses `split('\n')` — NOT `splitlines()` which treats `\x1e` as a line boundary)
- Orphan detection compares local directories against the **unfiltered** API repo list (via `list_repos(apply_visibility_filter=False)`) so that repos excluded by `include_forks`, `include_private`, `exclude_repos`, or `--project` filters are not falsely flagged as orphans
- **`--months N`**: only clone/pull repos pushed to within the last N months, via `filter_repos_by_activity()` in `filtering.py` (same `days/30.44` staleness formula as `RepoInfo.months_inactive`). Falls back to the account's `active_within_months` config field when the flag isn't passed; `None`/unset on both means no filtering (default, unchanged behavior). Applied after `exclude_repos`/visibility/`--project` filtering, so it doesn't affect orphan detection (which uses the unfiltered list)
- **Bitbucket accounts**: repo listing goes through `get_provider(account)` (returns `BitbucketClient` when `account.provider == "bitbucket"`), and `clone_repo()`/`fetch_and_pull()` are called with `auth_username=bitbucket_client.GIT_AUTH_USERNAME` (the fixed string `"x-bitbucket-api-token-auth"`) — NOT `account.auth_email`, which is only correct for the REST API's Basic auth, not git-over-HTTPS
- `_validate_name()`'s allowed-character set includes spaces (some real Bitbucket repo names contain them, e.g. "CUE Twitter Embed") — only `/`, `\`, and `..` are actually rejected as path-traversal risks. `clone_repo()`'s `GitError` on an invalid name is caught per-repo in the checkout loop (not propagated), so one bad name doesn't abort the whole run

## Audit command details
The `audit` command uses a **local-first** approach:
- Scans `data_dir/{slug}/public/` and `data_dir/{slug}/private/` for local checkouts
- Extracts local metadata via `get_local_repo_metadata()`: README/LICENSE presence, default branch, pushed_at, size
- Enriches each repo via `GitHubClient.get_repo()` for API-only fields (stars, forks, language, description, topics, etc.)
- Gracefully handles deleted/404 repos — they still appear in the report with default API values
- `LocalRepoInfo` dataclass holds local scan results; `RepoInfo.from_local_and_api()` merges local + API data
- Shows helpful "run checkout first" message if no local repos found
- Health score (0-100) per repo: composite of README (20), license (20), description (15), activity (25), not-archived (10), low issues (10). Report includes Health column in tables, summary stats, and a Low Health (<50) section listing what's missing per repo
- **Bitbucket accounts**: enrichment goes through `get_provider(account)` (returns `BitbucketClient`). `BitbucketClient._translate_repo()` maps Bitbucket's repository object onto the same fields `RepoInfo.from_api_response()`/`from_local_and_api()` expect, but several have no Bitbucket Cloud equivalent and are always defaulted: `stargazers_count`/`forks_count` are always 0 (no stars/forks concept), `license` is always `None` (no license API field — the report shows **MISSING** even when a local LICENSE file exists, since `RepoInfo.license` reads from API data when present), `archived` is always `False` (no repo-level archived flag, so the health score's "not-archived" component always scores full marks), and `topics` is always `[]` (no topics concept)

## Access command details
Flat command. Generates an access report showing who has access to which repos at what permission level.
- `--account SLUG` or `--all` required. Requires a token (collaborator endpoint needs auth).
- `--sort name` (default, alphabetical) or `--sort id` (ascending GitHub user ID — lower ID = older account).
- `--project NAME` optional — filters repos to the named project. Supports the three-way pattern: project-only (all accounts in project), project+account, project+all. When active, reports go to `reports/{project.name}/`.
- Uses `get_provider(account)` (returns `GitHubClient` or `BitbucketClient`) — fully wired for Bitbucket accounts.
- Lists repos via `list_repos()`, applies `filter_excluded_repos()`, `filter_repos_by_visibility()`, then `filter_by_project()`.
- Fetches collaborators per repo via `list_collaborators()` using `ThreadPoolExecutor(max_workers=5)` + Rich `Progress`. On Bitbucket, `BitbucketClient.list_collaborators()` maps its 3-level read/write/admin permission scale onto GitHub's 5-level shape (`triage`/`maintain` always `False`).
- `RepoAccess` dataclass holds repo name/url/private flag + raw collaborator list from API.
- `AccessResult` dataclass holds account info + list of `RepoAccess`, with `unique_users` and `total_access_entries` properties.
- Report has two views: **Access Matrix** (users as rows, repos as columns, highest permission in cells) and **Per-Repo Detail Tables** (full permission breakdown per collaborator). Both views respect the `--sort` order.
- Report written to `reports/{slug}/access_report.md` (or `reports/{project.name}/` when project is active).
- Terminal summary: total repos, unique collaborators, total access entries, repos with 2+ collaborators.

## Members command details
Click group with `list` and `remove` subcommands. Org-only for GitHub — errors if account type is not `org`, unless `account.provider == "bitbucket"` (Bitbucket accounts are always workspace-scoped, with no GitHub-style user-vs-org distinction, so the org-only guard is skipped for them).
- `list` — `--account SLUG` or `--all` (`--all` includes org-type accounts plus any Bitbucket accounts, since Bitbucket accounts are typically configured with `type: "user"`). Uses `get_provider(account)` (returns `GitHubClient` or `BitbucketClient`). For Bitbucket accounts, `account.workspace` (not `account.username`) is passed to `list_org_members()` and used as the display identifier, since it's the actual API path segment. Rich table: Login, ID.
- `remove` — `USERNAME` argument, `--account SLUG` required. Calls `click.confirm()` before removal. Still hardcodes `GitHubClient` (not wired to `get_provider()`) — not implemented for Bitbucket: an explicit early guard prints an error and exits when `account.provider == "bitbucket"`, explaining that Bitbucket Cloud's REST API has no endpoint for removing workspace members (membership changes go through Atlassian Admin or SCIM only).

## Collaborators command details
Click group with `list`, `add`, and `remove` subcommands.
- `list` — `--account` required, `--repo` optional (default: all repos). Rich table per repo showing permissions. Uses `get_provider(account)` — wired for Bitbucket accounts (via `BitbucketClient.list_collaborators()`, see Access command details above for the permission-mapping note).
- `add` — `USERNAME` argument, `--repo` or `--all-repos` required. `--permission` choice: pull/push/admin/maintain/triage (default: push). Confirms on `--all-repos`. Still hardcodes `GitHubClient` (not wired to `get_provider()`) — not implemented for Bitbucket: an explicit early guard prints an error and exits when `account.provider == "bitbucket"`, explaining that Bitbucket's per-repo permission-grant API requires the target user to already be a workspace member (no GitHub-style "invite an outside collaborator"), may return 402 Payment Required on Bitbucket's Free plan tier, and may only support legacy App Password auth rather than the API token auth this tool uses — so it needs verification against a live Bitbucket workspace before it can be built.

## Activity command details
Flat command. Tracks developer activity (commits, PRs, issues, reviews, tags) across repositories.
- `--account SLUG` (repeatable) or `--all` required. Two or more `--account` flags, or `--combine` with `--all`/`--project`, run `run_combined_activity()`: each account is scanned by `_scan_account()` (returns an `_AccountScan`; per-account token, data dir, fetch), then `_build_result()` backfills logins across every repo of every account, applies `--user`, aggregates one leaderboard, labels repos `owner/name`, and the report (with a Per-Account Summary) goes to `reports/combined/` (or the project dir) as `activity_{since}_{until}_accounts-a+b.md`. A single `--account` still goes through `run_activity()` unchanged.
- `--since`/`--until` are whole days in `config.timezone` (validated `YYYY-MM-DD`); the default range is computed in that timezone. All date comparisons go through `DateWindow`/`local_date()`: git gets ISO timestamps, API `since` params get `window.api_since` (a UTC-date superset), and every API timestamp is compared as a local date.
- `--fetch/--no-fetch` (default fetch): `process_repo()` calls `fetch_repo()` first (Bitbucket accounts pass `BITBUCKET_GIT_AUTH_USERNAME`); skipped for `--no-fetch` and `local_only: true` accounts. Failures go to `RepoActivity.fetch_error` → `ActivityResult.fetch_errors` → a **⚠ Stale git data** header block and a yellow terminal line. `_describe_data_as_of()` builds the **Data as of** header line from FETCH_HEAD times. The test suite's autouse `_no_real_git_fetch` fixture patches `fetch_repo` and `get_merge_commits`.
- `--user USERNAME` — filter to a specific developer (matches git author name, email, or GitHub login).
- `--repo REPO` — filter to a specific repo.
- `--since YYYY-MM-DD` / `--until YYYY-MM-DD` — date range (default: last 30 days).
- `--local-only` — never call the hosting API; report from local checkouts alone (commits, tags, branches; no PRs/issues/reviews). `run_activity(local_only=)` resolves a `local_reason` in priority order: the flag (`"--local-only"`), `account.local_only` (`"local_only: true in config"`), no token (`"no token configured"`), or an `AuthenticationError` from `validate_token()` (`"API authentication failed: ..."`) — which now closes the client and continues instead of `sys.exit(2)`, since an account whose access has ended still has its checkouts. The reason is printed in yellow before the scan, shown as a `Data source:` line in the terminal summary, stored on `ActivityResult.local_only_reason`, and rendered by the report as a `**Data source:** Local git only (...)` line directly under the Mode line. With no API data `_closed_pr_branches()` has nothing to skip, so every active branch is reported.
- `--branches` — split activity into default branch vs feature branches with no double-counting. Default branch commits are counted via `origin/{default_branch}`, and unmerged branch commits (NOT reachable from default) are shown in a separate "Branch Activity" section. Branch commits are deduplicated by **patch-id** (`get_patch_ids()` in `git_ops.py`: `git log -p ... | git patch-id --stable`, SHA→patch-id, `{}` on failure so a missing repo or old git degrades to SHA matching): a branch commit whose patch is already on the default branch in range (a rebased/cherry-picked copy) is dropped everywhere, and across branches the first occurrence wins for `RepoActivity.branch_commits`. Branches in `_closed_pr_branches(prs)` — every PR with that `head.ref` is closed (merged or declined), none open — are skipped before any git call: the work either landed via the default branch or was abandoned, and counting the branch again double-counted re-landed copies (seen live: three closed print-editions PRs whose work was re-landed under new PRs). `BitbucketClient.list_pulls()` emits `head.ref` from `source.branch.name` for this. Without this flag, `--all` is used for comprehensive counting (includes unmerged branch work, but may double-count squash-merged commits).
- Hybrid approach: local git for commits and tags (fast, no API limits), GitHub API for PRs/issues/reviews and email→login resolution. Line counts exclude non-authored content via `EXCLUDED_PATHSPECS` in `git_ops.py` (lock files, vendor dirs, WP core, minified assets).
- Scans local checkouts via `scan_local_repos()`, applies `filter_excluded_repos()`.
- For each repo (threaded with `ThreadPoolExecutor(max_workers=5)` + Rich Progress):
  - Runs `get_commit_log()` for the date range (default: `--all`; with `--branches`: `default_branch` param for main-only). Uses `--no-merges`, `\x1e` field separator, `split('\n')` not `splitlines()`. Commit `date` is the **committer** date (`%cI`, also in `get_branch_commits()`): git's `--since`/`--until` select by committer date, so every returned commit falls inside the range and Daily/Weekly breakdowns sum to the total; rebased/cherry-picked work counts on the day it was rebased.
  - Runs `get_tags_in_range()` to extract tags from local git refs (annotated + lightweight).
  - If `--branches`: runs `list_active_branches()` then `get_branch_commits()` per branch, builds `BranchActivity` objects with their own (possibly overlapping) developer aggregation for per-branch display. Separately, commits are deduplicated by SHA across all of the repo's active branches (a commit reachable from two stacked/overlapping branches, e.g. a release branch built on several feature branches, must only count once) into `RepoActivity.branch_commits`/`branch_developers` — the source used by anything that rolls branch activity into account-wide totals.
  - If token available: fetches PRs (`list_pulls(since=window.api_since)` — stops paginating at the first page holding a PR last updated before `since`, so a repo with thousands of historical PRs costs 1–2 requests instead of one per 100 PRs), issues (`list_repo_issues`), review comments (`list_review_comments`), PR conversation comments (`list_issue_comments`, filtered by `_pr_conversation_comments()`), `get_pull()` for each PR merged in the window that lacks `merged_by` (one request per merged PR; Bitbucket's translation always sets it from `closed_by`), and API commits (`list_repo_commits`, capped at 3 pages) to build email→login mapping.
  - PR states (`_pr_state_at`, `_pr_open_at_end`, `_pr_closed_unmerged_in`): state is as at the end of `until` (merged/closed after the window → open for it); closed-unmerged PRs are closed, never open; "open at end" also requires the PR to be opened or updated in the window — counting every open PR put fifteen people whose only "activity" was a months-old PR on the leaderboard. `_count_prs()` returns (opened, merged, open_at_end, closed_unmerged).
  - Merge commits: `get_merge_commits()` on the same refs as the commits (`--all`, or with `--branches` the default branch plus the active, non-closed-PR branches) → `RepoActivity.merge_commits` and `DeveloperActivity.merge_commits`; never in commit counts or lines.
  - If token available: fetches submitted PR reviews (`list_pull_reviews`, one request per PR) for PRs that `_pr_may_have_reviews_in_range()` keeps — those with `updated_at >= since` and `created_at <= until`. Safe because submitting a review bumps the PR's `updated_at`/`updated_on` (verified live on both GitHub and Bitbucket: PRs whose last event is a review have `updated_at` equal to that review's timestamp, and no review was ever later than `updated_at`). `_build_review_records()` turns them into `ReviewRecord`s, skipping unsubmitted (pending) reviews, reviews on the reviewer's own PR, and `COMMENTED` reviews with an empty body (GitHub records every inline-thread reply as one; their inline comments are already counted in `review_comments`). "Reviews" (all kept states, incl. `dismissed`) and "Approvals" are separate from "Review Comments" (inline line comments from `list_review_comments`) — a reviewer who writes their feedback in the review body leaves zero inline comments, so before reviews were counted their review work showed as 0.
  - Builds `PRRecord` list from raw API PR data with date filtering and merge status detection.
- **Developer merging**: Uses API-sourced `email_to_login` mapping to resolve git author emails to GitHub logins. Commits and API data (PRs/issues/reviews) are keyed by `login.lower()` when a mapping exists, enabling automatic merging without heuristics. Falls back to noreply email extraction (`_login_from_noreply()`) and email-based keying. A cross-repo backfill step applies the combined mapping to all per-repo developers, including `branch_developers`, before aggregation. Cross-repo aggregation in `_aggregate_developers_from_repos()` folds in both `repo.developers` (default branch + PR/issue/review/tag activity) and `repo.branch_developers` (deduped feature-branch commits) — without this, a developer whose only in-range activity is on an unmerged branch (an open PR still being iterated on) would be silently absent from the Developer Leaderboard, Developer Detail, and active-developer count despite appearing correctly in the per-repo Branch Activity table. `config.developer_aliases` is split by `_build_alias_lookups()` into email→login (seeded into every repo's `email_to_login` and the combined map) and name→login (passed as `name_to_login` to `_aggregate_developers()`, whose `_resolve_email_key(email, name)` tries API mapping, noreply email, then the name alias — and on a name-alias hit records the email into the caller's `email_to_login` dict, which is why that function must not replace an empty dict with `or {}`); the cross-repo backfill also applies name aliases. Keys by `github_login.lower()` when available, with `_merge_by_name()` as a secondary fallback: a union-find over shared identities — normalised name (`re.sub(r"[^a-z0-9]", "", name.lower())`), normalised `github_login`, and `_email_identity()` (an email's normalised local part, ≥ 8 chars, not a generic mailbox, noreply or `login@github` placeholder; merges `sarah.campion@acmecorp.example`/`@acmepublishing.example` and domain typos) — transitive, each group folding into the entry with most commits (merges `Anton Zorin`/`Anton-Zorin` and `Fiona Vale`/`fionavale`); normalised names and logins under 4 chars are never merged on (so `A B` entries stay separate). `madler` vs `Mohan Adler` is deliberately not mergeable. `_collect_dev_commits()` (Developer Detail's per-commit table) searches both `r.commits` and `r.branch_commits`.
- `_filter_repo_by_user()` filters commits, developers, PRs, tags, branches, review records (by reviewer login), and the deduped `branch_commits`/`branch_developers` at the data layer before report generation. A repo is kept if the user has any commits, PRs opened or merged, issues, review comments, submitted reviews, tags, or branch work there — so a repo where they only reviewed still appears. Matches by name, email, or GitHub login.
- Builds `ActivityResult` (includes `email_to_login` mapping, `total_branch_commits` property — sums the deduped `r.branch_commits` per repo, not a raw sum over `r.branches[*].commits`, which can double-count shared commits across overlapping branches), generates report via `generate_activity_report()`.
- Report filename encodes options: `activity_{since}_{until}[_accounts-{a}+{b}][_user-{user}][_repo-{repo}].md` in `reports/{slug}/` (combined: `reports/combined/`).
- Local-only reports (`RepoActivity.api_available`/`ActivityResult.api_available` False): PR, issue, review and comment cells and Summary rows read `n/a` (`NOT_AVAILABLE`), not 0, with a legend line.
- Branch dedup keeps one commit per patch-id across branches: `_earliest_copies()` picks the earliest `CommitRecord.committed_at` (full %cI timestamp), so a later "pulled in" re-commit by someone else on a QA branch isn't credited instead of the original (seen live on Bitbucket). The default branch's copy still wins over any branch copy.
- Report additions: **Date range** line names the timezone; **Data as of** line; **⚠ Stale git data** block (fetch failures); Summary rows for merge commits, PRs closed without merging, PRs still open at end of window, PR conversation comments; Leaderboard/Per-Repo Detail columns Merge Commits, Merges (`prs_merged_by`) and PR Comments with a legend line; **Data Quality: Lines Excluded From Counts** table (per developer, `excluded_*`, only when non-zero); Developer Detail "PRs merged (by them, any author)"; combined reports add **Accounts** and a Per-Account Summary.
- Developer display: `_dev_display_name()` returns GitHub login (plain, no `@` prefix) when available, otherwise human name. A **Contributors** lookup table at the top of the report maps each developer's display ID to their human name and email.
- Report header includes **Mode** line: "All branches" or "Default branch + feature branches (no double-counting)".
- Report sections: header **⚠ Data quality** block (only when `result.api_errors` is non-empty — populated from every scanned repo before the `--user` filter, falling back to `r.api_errors` on `result.repos`; sits right under the Mode line and lists each affected repo with its failed calls), Contributors (ID→name→email lookup, humans only), Summary (with net lines, PRs opened/merged/still open, PR reviews submitted, PR approvals, review comments, tags; `Active developers` counts humans only; an `of which by bots` commits row appears when bots are present so Leaderboard + Automation reconciles to `Total commits`), Developer Leaderboard (humans only, sorted by net lines, with commits, +lines, -lines, net lines, merged PRs, open PRs (`prs_open`, never `prs_opened - prs_merged`), issues, reviews, approvals, review comments, tags), Automation (bots — `_is_bot()`: `github_login` or `name` ends with `[bot]`, case-insensitive — same columns, directly after the Leaderboard; bots stay in Summary totals, are skipped by Contributors/Developer Detail, and `_top_contributor()` prefers humans, naming a bot only when no human contributed), Daily Breakdown (every day in range including zeros, with net lines), Weekly Breakdown (rows in insertion/chronological order — never `sorted()` on the labels, which put Oct before Sep; date ranges starting from the Monday on or before `--since`; weeks cut by the range are clipped and labelled `(partial)`, e.g. `Oct 03 – Oct 04 (partial)`, so every in-range commit lands in a row, with net lines), Per-Repo Activity (sorted by net lines, with net lines column, merged/unmerged PRs, reviews, tags, top contributor), Per-Repo Detail (sorted by net lines, developer tables sorted by net lines, full tables with all columns including net lines), Branch Activity (when `--branches`; per-repo tables of unmerged branch commits with net lines and top contributor), Developer Detail (sorted by net lines, per-developer commits with GitHub links oldest-first, PRs with links and status, PR reviews submitted oldest-first with PR author and outcome, tags with release links).
- Commit totals everywhere use `RepoActivity.all_commits` (default-branch + deduped feature-branch commits, which are disjoint): Summary "Total commits"/"Active repos", Daily/Weekly Breakdown, Per-Repo Activity, and `ActivityResult.total_commits`. Per-Repo Detail and the Per-Repo top contributor merge `r.developers` with `r.branch_developers` via `_aggregate_developers_from_repos([r])`. Without this, `--branches` reports had a Summary/Daily total lower than the Leaderboard total, and a repo whose only in-range work was on unmerged branches showed 0 commits in Per-Repo Activity. The Leaderboard and Per-Repo Detail share `_DEV_TABLE_HEADER`/`_dev_table_row()`. Cross-repo aggregation (`_add`, `_merge_by_name`) uses `DeveloperActivity.merged_with()`, which sums every count field generically, and `_aggregate_developers()` initialises counts from `_DEV_COUNT_FIELDS`, so a new count field needs no aggregation changes (the three hand-written constructors that used to drop new fields are gone).
- Pre-flight (GitHub accounts with a token, after `validate_token()`): `_print_rate_limit_preflight()` reads `client.last_rate_limit` — the `x-ratelimit-*` headers `_request()` captures from every response, here the preceding `/user` call — and prints remaining/limit and reset time (falls back to `get_rate_limit()`; confirmed live that `GET /rate_limit`'s body can report a token as unused while real response headers show 1,800+ used in the same window, so headers are the source of truth), in yellow when remaining < `RATE_LIMIT_WARN_BELOW` (500). The token shares one 5,000/hour bucket with everything else using it (e.g. the `gh` CLI).
- API failures are never silent: each `except Exception` in `process_repo()` records `"call: error"` in the repo's `api_errors` and logs at WARNING (visible without `--verbose`). `_filter_repo_by_user()` carries `api_errors` through. A rate-limited scan previously wrote a report of all-zero PR/review figures with only DEBUG lines to show for it.
- Terminal summary: date range, total commits (incl. branch commits), active developers, PRs opened, issues opened, PR reviews submitted, tags created. With `--branches`: also shows branches with activity and branch commit count. If `activity_result.api_errors` is non-empty (collected from every scanned repo before the `--user` filter), a red `API data incomplete for N repo(s): ...` line follows.
- Works without a token (commits and tags from local git, no API data) — reported as `Data source: Local git only (no token configured)`.
- **Bitbucket accounts**: API-sourced data (PRs, issues, review comments, commits for email→login mapping) goes through `get_provider(account)` (returns `BitbucketClient`), which translates Bitbucket's PR (OPEN/MERGED/DECLINED/SUPERSEDED → open/closed+merged_at), issue (collapses Bitbucket's states to open/closed), and commit-author (`author.raw` regex-parsed into name/email) shapes into the GitHub-shaped dicts `activity.py` expects. Login resolution uses Bitbucket's `nickname`/`display_name` fields as the closest equivalent to GitHub's public `login` (Bitbucket removed public usernames for GDPR compliance in 2019, except for the currently authenticated user). `list_pulls()` defaults `per_page` to 50, not the Protocol's 100 — Bitbucket's `/pullrequests` endpoint specifically caps `pagelen` at 50 and returns 400 "Invalid pagelen" above that; at 100 every call fails and is silently swallowed by `activity.py`'s generic `except Exception`, so no PRs are ever fetched for the account. Review comments have no repo-wide endpoint on Bitbucket, so `list_review_comments()` fans out per-PR and aggregates — when `since` is given, PRs whose `updated_on` predates it are skipped before the per-PR fetch (a PR untouched since `since` can't have comments after it, since Bitbucket bumps `updated_on` on new comment activity), since firing one request per PR ever created in a repo's history can exhaust Bitbucket's API rate limit during a multi-repo scan and cause unrelated calls on other repos to start failing with 429s. All per-repo API calls in `activity.py`/`audit.py`/`readme.py` pass `lr.repo_slug` (see `git_ops.py`), not `lr.name` — Bitbucket's display name (used for the checkout directory, since it's the readable identifier) can contain spaces/caps that differ from the actual URL-safe slug a repo's REST endpoints require (e.g. name="Bundler JS", slug="bundler-js"); using `name` 404s. `BitbucketClient._request()` retries on 429 (sleeping the `Retry-After` duration, within `MAX_RETRIES`) rather than raising immediately, since Bitbucket's burst limiter resets in seconds — **known gap**: confirmed live against a 396-repo account that a 5-worker concurrent scan still exhausts all retries for roughly half the repos (the limiter is a sustained/rolling one that 5 concurrent workers can refill faster than it drains), so very large accounts still undercount PRs/issues/reviews on a full scan; a proper fix needs a shared rate limiter/semaphore across concurrent requests rather than per-request retry, not yet implemented. Submitted reviews on Bitbucket come from `BitbucketClient.list_pull_reviews()` (the PR `/activity` feed's approvals and change requests; Bitbucket has no "comment review", and PR comments are already counted as review comments), and add one more per-PR request on top of `list_review_comments()`'s fan-out for every PR updated in range, which adds to the rate-limit gap above. `stars`/`topics`/`archived`/`license` gaps (see Audit command details) don't affect activity, since it doesn't read those fields.

## GitHub API exceptions
`github_client.py` defines three exception classes:
- `GitHubAPIError(message, status_code=None)` — base class for all API errors
- `AuthenticationError` — raised on 401 (invalid/expired token)
- `RateLimitError` — raised on 403 when `x-ratelimit-remaining` is 0

All commands catch `AuthenticationError` after `validate_token()`. The client retries on 5xx errors and network failures (up to `MAX_RETRIES=3` with `RETRY_BACKOFF=1.0s`). A primary rate limit does not consume a retry: `_request()` waits for the reset and retries once (see `github_client.py` in Key files); `RateLimitError` is raised only if the retry is also rate-limited.

## Code review checklist (common pitfalls)
When writing or modifying code, avoid these confirmed issues:
1. **Console initialization** — every `Console()` instance MUST use `Console(soft_wrap=True, force_terminal=True)` — never bare `Console()`. This ensures ANSI colour codes are emitted when output is redirected (e.g., cron logs viewed with `tail -f`).
2. **Temp files with secrets** — never create a temp file with default permissions and `chmod` afterwards (TOCTOU race). Use `os.open()` with `O_CREAT | O_EXCL` and explicit `0o700` mode from creation. Always log a warning if cleanup fails — never silently `pass` on `OSError` during `os.unlink()` of secret-bearing files.
3. **GitHubClient lifecycle** — always use the `with GitHubClient(account) as client:` context manager pattern. Never manually call `client.close()` — an exception between creation and close leaks the HTTP connection.
4. **Pagination safety** — any loop consuming paginated API results must have an absolute upper-bound page limit (e.g., 1000) as a safety net against infinite loops from malformed responses, even if the primary termination condition is an empty result set.
5. **Report helper bounds** — visual output helpers (bar charts, tree builders) must clamp inputs and cap output size. Unbounded computation on user-controlled data can produce megabytes of output.

## Adding new commands
1. Create `src/auditer/commands/<domain>/<name>.py` (domain: `data/`, `repo/`, `people/`, or root for meta/utility)
2. Define a Click command function decorated with `@click.command("name")`
3. Use `@click.pass_context` to access `ctx.obj["lazy_config"].config` for the loaded AppConfig
4. Register in `src/auditer/cli.py` with `cli.add_command()`
5. If it generates output, write to `reports/{slug}/`
6. If it's destructive, add a confirmation prompt
7. Add tests in `tests/commands/<domain>/test_<name>.py` (mirroring source structure)
